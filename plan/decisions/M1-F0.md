# F0: the agents' login

**Decision: pass.** The agents act as the GitHub App `one-launch-agents`. The fallback, a bot account in an organization that owns the repo, is not needed.

How to use it is in `../design/workflow.md` › "Acting as the app".

## Checked

| What | Result |
| --- | --- |
| A token minted from the app's key | 0.4 s with PowerShell 7 alone, no added dependency. The token reaches this repo only, with contents and pull requests, and lasts 60 minutes |
| The app's permissions | Contents write, pull requests write, metadata read. No webhook events |
| Where the app is installed | One installation, on the owner's account, limited to selected repositories: this repo and no other |
| `git` as the app | A branch pushed over HTTPS. Its commits carry the app's name and noreply address. The checkout's own remote and identity are untouched |
| `gh` as the app | GitHub names the caller `one-launch-agents[bot]`, without admin rights |
| A workflow file pushed as the app | Refused by GitHub: "refusing to allow a GitHub App to create or update workflow `.github/workflows/ci.yml` without `workflows` permission". The branch was not created |
| The rulesets, read back | `main`: pull requests only, squash only, code-owner review, no bypass. Tags: creation, update and deletion blocked for all but the admin role |

`scripts/agent/check.ps1` repeats rows two and three on demand and exits non-zero on any difference.

## How a workflow file reaches a pull request

The app cannot push one, and that stays so: it is what keeps an agent from weakening CI. The agent commits the workflow change on its branch and stops. The owner pushes that commit from the owner's checkout, the app opens the pull request, and the owner approves it as code owner once the owners file exists (F6). The ruleset allows this: it asks for no approval of the last push.

By GitHub's rules a pull request opened by the owner that touches an owner-approved path could not merge once the owners file exists: nobody approves their own pull request, and the owner is the only code owner. So the app opens every pull request, including the ones the owner pushes to. F6 checks both halves with the owners file in place.

## Found here, for later tickets

- **F6, hooks.** The owner's own logins are present on this PC: `gh` is signed in as the owner, and the checkout's remote uses the owner's SSH key. Both have admin rights, which include approving a pull request, changing a ruleset and bypassing the tag ruleset. The hooks must keep agent sessions on `scripts/agent/git.ps1` and `scripts/agent/gh.ps1`: block a bare `gh` that changes anything, `gh auth`, any push not made through the wrapper, and any call of `git-credential.ps1` other than by git.
- **F6, owners file.** `scripts/agent/` belongs on the owner-approved list: a change there could ask for a different token.
- **F7, slots.** A slot is a clone over HTTPS whose local config holds what `git.ps1` passes per call (name, address, credential helper, SSH off), so plain git in a slot is the app.
- **Cost.** Each wrapped `gh` call and each push mints a token: two requests, about 0.4 s. If a wave makes this noticeable, cache the token in memory of a long-lived helper, not on disk.
- **Branches.** The repo keeps a merged pull request's branch. The app may delete its own; or the owner turns on "Automatically delete head branches".
